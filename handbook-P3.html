P3.3 · Extract with a forced tool and a schema

25 min · 4.3 2.3

The one idea: you do not ask Claude to "reply in JSON". You give it a tool whose input is your form, and you force it to call that tool. The API then returns the form already filled in, in the right shape.

Four terms:

  • Tool: a named action Claude can call. Here the tool record_invoice does nothing itself. Its only job is to make Claude fill in its input.
  • input_schema: the JSON schema of the tool's input, which is your form.
  • tool_choice: tells Claude whether it must call a tool. {"type":"tool","name":"record_invoice"} means "you must call exactly this tool".
  • Nullable field: a field whose type is ["string","null"]. Claude may answer null, which means "the document does not say".

P3.3.1 · Create the extractor

Paste into Claude Code:

Create extract.py with exactly this content, and nothing else. Do not run it.

"""P3: extract invoice data with tool_use and a JSON schema."""
import json
import pathlib
import sys

import anthropic

MODEL = "claude-sonnet-5-5"  # check docs.claude.com for current model names
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

INVOICE_TOOL = {
    "name": "record_invoice",
    "description": "Record the data from ONE invoice. Use null for any field the document does not state. Never guess.",
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor": {"type": "string"},
            "invoice_number": {"type": ["string", "null"]},
            "invoice_date": {"type": ["string", "null"], "description": "YYYY-MM-DD"},
            "due_date": {"type": ["string", "null"], "description": "YYYY-MM-DD. null if the document gives no date."},
            "currency": {"type": "string", "enum": ["EUR", "USD", "GBP", "INR", "other", "unknown"]},
            "currency_detail": {"type": ["string", "null"], "description": "Only when currency is 'other'"},
            "category": {"type": "string", "enum": ["software", "hardware", "services", "other"]},
            "category_detail": {"type": ["string", "null"], "description": "Only when category is 'other'"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "amount": {"type": "number"},
                    },
                    "required": ["description", "quantity", "amount"],
                },
            },
            "stated_total": {"type": ["number", "null"], "description": "The total exactly as written on the invoice"},
            "calculated_total": {"type": "number", "description": "The sum of the line item amounts"},
            "conflict_detected": {"type": "boolean", "description": "True if stated_total and calculated_total differ"},
        },
        "required": [
            "vendor", "invoice_number", "invoice_date", "due_date", "currency", "currency_detail",
            "category", "category_detail", "line_items", "stated_total", "calculated_total", "conflict_detected",
        ],
    },
}

SYSTEM = "You extract invoice data. Copy what the document states. If a value is not in the document, use null. Do not infer or invent values."

FEW_SHOT = """

Category rules, with examples:
- "Annual licence for design software" -> software (the thing bought is the software itself).
- "Engineer installed and configured the firewall, 5 hours" -> services (people's time, even when the subject is software or hardware).
- "Two monitors delivered and installed" -> hardware (the thing bought is a device; installation is a small part).
- Laptops bought AND engineer hours billed, with neither clearly the main item -> other, category_detail "mixed: hardware + services".
"""


def extract(text: str, extra_system: str = "") -> dict:
    response = client.messages.create(
        model=MODEL,
        max_tokens=1024,
        system=SYSTEM + extra_system,
        tools=[INVOICE_TOOL],
        tool_choice={"type": "tool", "name": "record_invoice"},
        messages=[{"role": "user", "content": f"\n{text}\n"}],
    )
    for block in response.content:
        if block.type == "tool_use":
            return block.input
    raise RuntimeError(f"No tool call. stop_reason={response.stop_reason}")


if __name__ == "__main__":
    use_examples = "--few-shot" in sys.argv
    files = [a for a in sys.argv[1:] if not a.startswith("--")]
    files = files or sorted(str(p) for p in pathlib.Path("docs").glob("*.txt"))
    out = pathlib.Path("out")
    out.mkdir(exist_ok=True)
    for f in files:
        data = extract(pathlib.Path(f).read_text(), FEW_SHOT if use_examples else "")
        name = pathlib.Path(f).stem
        (out / f"{name}.json").write_text(json.dumps(data, indent=2))
        print(f"\n=== {name} ===\n{json.dumps(data, indent=2)}")

Type /exit. Then read the file in Antigravity and find these four lines. They are the whole lesson:

LineWhat it does
"due_date": {"type": ["string", "null"] ...}Allows "not stated" as an answer
"enum": [... "other", "unknown"] plus currency_detailA fixed list of answers, with a way out for values not on the list
"stated_total", "calculated_total", "conflict_detected"Claude records both totals and flags a mismatch instead of picking one
tool_choice={"type": "tool", "name": "record_invoice"}Forces the form to be filled in, every time

  • b-email: invoice_number: null. The dates are turned into 2026-10-02 and 2026-10-30.
  • c-missing: due_date: null and currency: "unknown". Nothing was invented.
  • d-conflict: stated_total: 1730, calculated_total: 1630, conflict_detected: true.

The exam lens, in plain words.

1. You need output in a fixed shape: define it as a tool's input schema and use tool_use. The shape is then guaranteed. Asking for JSON in the prompt is not.

2. You need the tool called every time: force it with tool_choice set to that tool. "any" means "call some tool, your choice". "auto" lets Claude answer in plain text instead.

3. A field the document may not contain: make it nullable. Then "not stated" is a valid answer and Claude does not have to invent one.

4. A fixed list of values that real life can break: add "other" plus a detail field, so new cases are captured instead of forced into a wrong box.

5. The schema fixes the shape, not the truth. Totals that do not add up still pass the schema. That is why you record both totals and a conflict flag.

Trap answer to spot: "add 'return valid JSON only' to the prompt". The tool and schema guarantee the shape. A sentence in the prompt does not.

P3.5 · Few-shot examples for the hard cases

20 min · 4.2

The one idea: some choices are judgment calls. Is setting up software "software" or "services"? A rule in words leaves room to interpret. A few worked examples show exactly where the line is.

One term:

  • Few-shot examples: a few worked examples in the prompt that show the right answer for tricky cases. Look at FEW_SHOT in extract.py: four examples, each with the reason.

P3.5.1 · The consistency test

Start Claude Code and paste:

Create consistency.py with exactly this content, and nothing else. Do not run it.

"""Run the two ambiguous invoices 3 times each, without and with few-shot examples."""
import pathlib

from extract import FEW_SHOT, extract

DOCS = ["docs/b-email.txt", "docs/e-ambiguous.txt"]

for label, extra in [("WITHOUT examples", ""), ("WITH examples", FEW_SHOT)]:
    print(f"\n--- {label} ---")
    for d in DOCS:
        text = pathlib.Path(d).read_text()
        results = []
        for _ in range(3):
            r = extract(text, extra)
            results.append(f"{r['category']} ({r['category_detail']})")
        print(f"{pathlib.Path(d).stem:14} {results}")

Type /exit, then run it. It makes 12 calls and takes about a minute:

uv run python consistency.py

Checkpoint ✅ Compare the two blocks:

  • Without examples, the category may change between runs, or be a reasonable answer that differs from your team's rule.
  • With examples, b-email is other (mixed: hardware + services) and e-ambiguous is services, the same in all three runs.

If both blocks are already identical, that is a fair result too: the model was consistent on these two. Then look at whether the answer without examples matches your team's rule. Consistent is not the same as right. The examples make it right.

The exam lens, in plain words.

1. Output varies, or lands on the wrong side of a fuzzy line: add 2–4 examples of exactly those borderline cases, with the reason for each.

2. Pick examples from the cases that actually go wrong, not easy ones. An example of an obvious case teaches nothing.

3. Examples also fix format: different document layouts (an email, a table, a receipt) all end up in the same fields.

Trap answer to spot: "write a longer, more detailed rule in the prompt". More words about a fuzzy line keep it fuzzy. Examples draw the line.

P3.7 · Quick reference card

Fixed shape: a tool's input_schema plus tool_use, not "reply in JSON".
Always fill the form: tool_choice: {"type":"tool","name":"..."}. "any" = some tool. "auto" = may answer in text.
May be missing: nullable type ["string","null"], so Claude says null instead of inventing.
Fixed list: enum + "other" + a detail field.
Shape ≠ truth: the schema cannot see that totals do not add up. Record both totals and a conflict flag.
Fuzzy line: 2–4 examples of the borderline cases, each with its reason.
