P2.1 · Set up and plant two bugs

10 min

The one idea: a reviewer is only worth testing if there is something to find. You break the P1 code on purpose, in two ways, and restore it in P2.6.

You need: P1 committed and pushed. In GitHub Desktop, "Changes" shows 0 files. If not, commit P1 first.

P2.1.1 · Make the P2 folder and its two files

In the Terminal, go to the repository root and start Claude Code there:

cd ~/Documents/GitHub/claude-architect-builds && mkdir -p p2-ci-review && claude

Paste:

Create p2-ci-review/criteria.md with exactly this content, and nothing else:

# Review criteria (team standard)

Report ONLY these three kinds of problem:
1. bug: the code does something different from what its name, docstring or tests say.
2. error-handling: an error can be raised or swallowed in a way the caller cannot handle.
3. security: untrusted input reaches something dangerous.

Do NOT report: style, naming, formatting, missing docstrings, missing type hints, "consider" suggestions, or anything you are not sure is a real problem.

For every finding give: file, line, category, one sentence on what goes wrong, one sentence fix.
If nothing meets these criteria, return no findings. No findings is a good result.

Then paste:

Create p2-ci-review/review-schema.json with exactly this content, and nothing else:

{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "file": {"type": "string"},
          "line": {"type": "integer"},
          "category": {"type": "string", "enum": ["bug", "error-handling", "security"]},
          "issue": {"type": "string"},
          "fix": {"type": "string"}
        },
        "required": ["file", "line", "category", "issue", "fix"]
      }
    }
  },
  "required": ["findings"]
}

P2.1.2 · Plant the two bugs

Still in Claude Code, paste:

This is a deliberate exercise: I am planting two bugs for a code reviewer to find. Make exactly these two changes and nothing else. Do not fix anything else, do not run tests, do not add comments that reveal the bugs.
1. In p1-team-setup/src/orders/service.py, make the function that lists orders drop the last order from its result (for example with a [:-1] slice).
2. In p1-team-setup/src/orders/api.py, in the function that cancels an order, convert the order id to a string with str() before passing it to the service.
Then tell me which two lines you changed.

Checkpoint ✅ Claude names two changed lines, one in each file. Type /exit.

Why these two. Bug 1 is local: you can see it by reading one file. Bug 2 is across files: api.py looks harmless alone. It only breaks because service.py stores order ids as numbers. P2.5 shows which review finds which.

P2.2 · Run Claude Code with no human

10 min · 3.6

The one idea: in CI, nobody is at the keyboard to answer questions. Claude Code must take one prompt, answer, and stop.

Two terms:

  • Headless: running with no screen and no human. You start it with -p (short for "print").
  • --allowedTools: the tools Claude may use without asking. With no human, anything that would need approval cannot happen.

Go into the P1 code folder. Every review in this guide runs from here, so the team's CLAUDE.md is loaded:

cd ~/Documents/GitHub/claude-architect-builds/p1-team-setup

Run a headless review:

claude -p "Review src/orders/service.py and list any bugs. Be brief." --allowedTools "Read,Grep,Glob"

Checkpoint ✅ Text prints, then the Terminal prompt comes back. No questions, no approval prompts. Claude Code ran once and stopped.

Now the same run, as data:

claude -p "Review src/orders/service.py and list any bugs. Be brief." --allowedTools "Read,Grep,Glob" --output-format json

Checkpoint ✅ One block of JSON. The review text is inside a field (usually "result"), with extra fields such as cost and duration. A CI program can read this. A human sentence it cannot.

The exam lens, in plain words.

1. In a pipeline, Claude Code always runs with -p. Without it, it waits for a person who never comes.

2. The team's CLAUDE.md is how the CI reviewer learns the team's standards. It loads in CI exactly as it does for a person.

3. A fresh headless run is an independent reviewer. The same session that wrote the code is a weaker reviewer of it, because it already "believes" its own reasoning.

Trap answer to spot: made-up flags or environment variables that sound plausible. Know the real ones: -p, --output-format json, --json-schema.

P2.3 · Vague review vs explicit criteria

15 min · 4.1

The one idea: "find any issues" invites noise. Developers stop reading a reviewer that cries wolf. Explicit criteria say what to report and what not to.

Two terms:

  • False positive: a finding that is not a real problem, for example a style opinion.
  • Explicit criteria: a written list of exactly which problems count.

P2.3.1 · The vague review

claude -p "Review src/orders/service.py and list every issue you find." --allowedTools "Read,Grep,Glob"

Count the findings. Mark each one: real bug or noise (style, naming, "consider", docstrings).

P2.3.2 · The explicit review

claude -p "$(cat ../p2-ci-review/criteria.md)

Review only this file: src/orders/service.py" --allowedTools "Read,Grep,Glob"

$(cat ...) pastes the whole criteria file into the prompt.

Checkpoint ✅ Fewer findings. The planted bug (the dropped last order) is still found. Most of the noise is gone. Write down both counts: vague __ findings, explicit __ findings.

The exam lens, in plain words.

1. Too many false positives: write down exactly which kinds of problem count, and say what must not be reported.

2. Ask for evidence with each finding (line, what goes wrong). It forces the reviewer to check before it reports.

3. Say that "no findings" is a good result. Otherwise the reviewer invents something to justify the run.

Trap answer to spot: "ask it to be more careful" or "only report high-confidence findings". Vague words do not cut noise. A written list does.

P2.4 · Findings as data

15 min · 3.6

The one idea: a CI system posts each finding as a comment on the exact line of code. It can only do that if every finding has the same fields every time. A schema forces that shape.

One term:

  • JSON schema: a description of the exact shape the data must have: which fields, which types, which values are allowed. Your review-schema.json is one.

Run, and save the result to a file:

mkdir -p ../p2-ci-review/out && claude -p "$(cat ../p2-ci-review/criteria.md)

Review only this file: src/orders/service.py" --allowedTools "Read,Grep,Glob" --output-format json --json-schema "$(cat ../p2-ci-review/review-schema.json)" > ../p2-ci-review/out/service-structured.json
  1. In the Antigravity Explorer, open p2-ci-review/out/service-structured.json.
  2. Press Shift+Option+F to format it.
  3. Find the findings. In current versions they are in a field such as "structured_output". In some versions they are inside "result".

Checkpoint ✅ Each finding has exactly file, line, category, issue and fix, and category is one of the three allowed values.

The exam lens, in plain words.

1. CI needs findings a program can read: use --output-format json together with --json-schema.

2. The schema fixes the shape. The criteria fix the content. You need both.

3. When a review runs again after new commits, give it the previous findings and ask for only new or still-open problems. Otherwise every comment is posted twice.

Trap answer to spot: "parse the text output with a script". Text changes shape from run to run. A schema does not.

P2.5 · File by file, then across files

20 min · 4.6

The one idea: one review of many files at once spreads its attention thin. Review each file alone first, then do one extra pass that looks only at how the files work together.

Two terms:

  • Per-file pass: one review per file, looking only at that file.
  • Integration pass: one review across files, looking only at problems between them.

P2.5.1 · Create the review script

Start Claude Code from the repository root:

cd ~/Documents/GitHub/claude-architect-builds && claude

Paste:

Create p2-ci-review/run_review.sh with exactly this content, then make it executable with chmod +x. Do not run it.

#!/bin/bash
# Multi-pass review: one pass per file, then one integration pass.
set -e
cd "$(dirname "$0")/../p1-team-setup"
OUT=../p2-ci-review/out
mkdir -p "$OUT"
CRITERIA="$(cat ../p2-ci-review/criteria.md)"
SCHEMA="$(cat ../p2-ci-review/review-schema.json)"

for f in src/orders/service.py src/orders/api.py src/orders/models.py; do
  name=$(basename "$f" .py)
  echo "Pass 1 (per file): $f"
  claude -p "$CRITERIA

Review only this file: $f. Ignore every other file." \
    --allowedTools "Read,Grep,Glob" \
    --output-format json --json-schema "$SCHEMA" > "$OUT/$name.json"
done

PREVIOUS="$(cat "$OUT"/service.json "$OUT"/api.json "$OUT"/models.json)"
echo "Pass 2 (integration)"
claude -p "$CRITERIA

You are the integration reviewer for src/orders/service.py, api.py and models.py.
Per-file reviews already ran. Their findings are below. Do NOT repeat them.
Report ONLY problems BETWEEN files: a caller that passes the wrong type or value to another module, names or types that do not match across files, errors that break across a call.

Per-file findings:
$PREVIOUS" \
  --allowedTools "Read,Grep,Glob" \
  --output-format json --json-schema "$SCHEMA" > "$OUT/integration.json"

echo "Done. Results in p2-ci-review/out/"

Type /exit.

P2.5.2 · Run it

./p2-ci-review/run_review.sh

It takes 2–4 minutes. You see four "Pass" lines.

P2.5.3 · Read the results

Open the four files in p2-ci-review/out/ and format each with Shift+Option+F.

Checkpoint ✅

  • service.json finds the dropped last order (bug 1, local).
  • api.json alone may or may not flag the str(). It looks harmless in one file.
  • integration.json either finds bug 2, or is empty because api.json already found it. Both are correct: the integration pass is told not to repeat earlier findings.

Why api.json can find a cross-file bug. The per-file reviewer has the Read tool, so it can open service.py to check how cancel_order works, even when told to review only api.py. To make a pass truly file-only, put the file's text in the prompt and give it no Read tool. Results also vary between runs.

The exam lens, in plain words.

1. A big review gives patchy, inconsistent results: split it. One focused pass per file finds local problems.

2. Add one separate pass that looks only at how the files connect. Local passes cannot see those problems.

3. Pass the earlier findings into the later pass, and tell it not to repeat them.

Trap answer to spot: "use a model with a bigger context window" or "tell developers to make smaller changes". The first does not fix thin attention. The second moves the problem to people.

P2.8 · Quick reference card

Headless: claude -p "..." runs once and exits. Always in CI.
Tool permission with no human: --allowedTools "Read,Grep,Glob".
Data, not text: --output-format json. Fixed shape: --json-schema.
Team standards in CI: CLAUDE.md, loaded as usual.
Independent review: a fresh run, not the session that wrote the code.
Fewer false positives: written criteria, what to skip, evidence per finding, "none is fine".
Big review: one pass per file, then one integration pass, earlier findings passed in.
Re-review after commits: pass previous findings, report only new or still open.
