P1.1 · The three ideas in plain words

5 min · read only

IdeaIn one sentenceWhat the exam tests
CLAUDE.mdA text file of standing instructions that Claude Code reads automatically. It can exist at three levels: you (user), the repository (project), and one folder (directory).Which level to use. Team rules go in the repository. Personal rules go in your home folder, which git does not share.
RulesSmall instruction files in .claude/rules/. Each one says which files it applies to, with a pattern such as tests/**/*.py.When a rule must follow a file type across many folders, a rule with a pattern beats a CLAUDE.md in one folder.
Commands and skillsA command is a saved prompt you start with /name. A skill is a packaged task that Claude can also start by itself, and it can run in a separate context.Where the file goes so the whole team gets it, and when to isolate a task with context: fork.

Three terms used below:

  • Frontmatter: settings at the top of a file, between two lines of ---.
  • Glob: a file pattern. * means any name. ** means any folder, at any depth.
  • Context: everything Claude can see in the current conversation. It has a size limit, so what goes in it matters.

P1.2 · Make the practice codebase

10 min

The one idea: you need a small, real-looking codebase to configure. Claude Code writes it. You do not need to read the code.

Paste this into Claude Code:

Create a small Python project in this folder for a fictional order-tracking service.
Structure:
- src/orders/ with models.py (Order dataclass), service.py (create, cancel, list orders, kept in memory), and api.py (three plain functions that call the service)
- tests/ with test_service.py and test_api.py, using pytest, 3 to 5 tests each
- docs/conventions.md with 5 short team coding conventions (naming, type hints, docstrings, error handling, test naming)
- a README.md of 10 lines or fewer
Keep every file short. Do not create a CLAUDE.md or anything under .claude/ yet. I will ask you to create them in later steps, and when I do, create them without asking again.
When done, list the files you created.

Claude Code asks for permission before it writes files. Approve each request.

Checkpoint ✅ Claude lists src/orders/, tests/, docs/conventions.md and README.md. There is no CLAUDE.md yet.

P1.3 · CLAUDE.md at three levels

20 min · 3.1

The one idea: each level answers a different question. Who am I? (user) · How does this team work? (project) · What is special about this folder? (directory).

By the end you can: say which level a rule belongs to, use @import to pull in another file, and prove with /memory which files are loaded.

LevelFile locationShared with the team?
User~/.claude/CLAUDE.mdNo. It is in your home folder, not in git.
Project./CLAUDE.md at the repository rootYes. Everyone who clones gets it.
Directory./tests/CLAUDE.md (any sub-folder)Yes. Loaded when Claude works with files in that folder.

P1.3.1 · The project level, with an import

Copy the whole box below — instruction and file together — and paste it into Claude Code as one message.

Create CLAUDE.md in this folder with exactly this content, and nothing else:

# Order service — team instructions

## Project
Small Python order-tracking service. Source in src/orders/, tests in tests/.

## Team standards
- Python 3.13. Type hints on every function.
- Run tests with: pytest -q
- Never add a new dependency without asking first.

## Conventions
@docs/conventions.md

What @docs/conventions.md does. It imports that file into CLAUDE.md. The conventions stay in one file that people can also read on their own. CLAUDE.md stays short.

P1.3.2 · The directory level

Copy the whole box below — instruction and file together — and paste it into Claude Code as one message.

Create tests/CLAUDE.md with exactly this content:

# Tests folder
- One assert per test where possible.
- Use pytest fixtures for any Order you build more than once.

P1.3.3 · The user level

This file is outside the repository. In the Terminal, Claude Code asks before it writes outside the project folder. Approve it.

Append these two lines to ~/.claude/CLAUDE.md (create the file if it does not exist). Do not change anything else in it:
- Explain every change in 2 sentences or fewer.
- I am preparing for the Claude Architect exam; when relevant, name the Claude Code feature you are using.

P1.3.4 · Prove what is loaded

  1. Type /memory and press Return.
  2. Read the list. It shows the memory files Claude Code found. Press Escape to close it.
  3. Type /exit, then start Claude Code again with claude. CLAUDE.md files load when a session starts.
  4. Paste this:

I am about to ask you to edit tests/test_service.py.
Before you do anything, list every instruction that applies to that edit.
For each one, name the exact file it came from (user, project, imported, or directory).
Do not edit anything.

Checkpoint ✅ Claude names instructions from all four sources: ~/.claude/CLAUDE.md, ./CLAUDE.md, docs/conventions.md (through the import) and tests/CLAUDE.md.

The exam lens. A new team member says Claude ignores a team rule that works for everyone else. First suspect: the rule is in someone's user file, not the project file. User-level files are never shared through git.

P1.4 · Path-specific rules

15 min · 3.3

The one idea: a directory CLAUDE.md follows a folder. A rule with a glob follows a file pattern, in any folder.

By the end you can: write a rule that applies only to matching files, and explain why it beats a directory CLAUDE.md when the files are spread out.

P1.4.1 · Make the files spread out

Create src/orders/test_models_inline.py with one small pytest test for the Order dataclass.
This is deliberate: a test file outside the tests/ folder.

P1.4.2 · Write the rule

Copy the whole box below — instruction and file together — and paste it into Claude Code as one message.

Create .claude/rules/testing.md with exactly this content:

---
paths:
  - "**/test_*.py"
---
# Testing rule
- Every test name starts with test_ and describes the behaviour, e.g. test_cancel_rejects_shipped_order.
- Never call a real network or file system in a test.

P1.4.3 · Test it

Type /exit, start claude again, and paste:

List the instructions that apply when you edit src/orders/test_models_inline.py, and the file each comes from.
Then do the same for src/orders/service.py.
Do not edit anything.

Checkpoint ✅ The testing rule applies to test_models_inline.py. It does not apply to service.py. tests/CLAUDE.md does not apply to either, because neither file is in tests/.

The exam lens. Test files sit next to the code in many folders, and the team wants one testing standard. Answer: a .claude/rules/ file with a glob. Not a CLAUDE.md in every folder, and not one long root CLAUDE.md that loads for every file.

P1.5 · A team slash command

15 min · 3.2

The one idea: the folder decides who gets the command. .claude/commands/ in the repository is for the team. ~/.claude/commands/ is only for you.

P1.5.1 · The team command

Copy the whole box below — instruction and file together — and paste it into Claude Code as one message.

Create .claude/commands/review.md with exactly this content:

---
description: Review one file against the team checklist
argument-hint: [file path]
allowed-tools: Read, Grep
---
Review $ARGUMENTS against this checklist. Report only real problems.

1. Every function has type hints.
2. Errors are raised with a clear message, never silently ignored.
3. Names follow docs/conventions.md.

For each problem give: line number, rule number, one-sentence fix.
If there are no problems, say "No issues found".

Three terms in that file:

  • $ARGUMENTS: whatever you type after the command name.
  • argument-hint: the hint Claude Code shows while you type the command.
  • allowed-tools: the only tools the command may use without asking. Here Claude can read but cannot edit.

P1.5.2 · Run it

  1. Type /exit and start claude again.
  2. Type /rev and look at the suggestion list. Your command shows with its description and hint.
  3. Run:
/review src/orders/service.py

Checkpoint ✅ Claude returns a short list, or "No issues found", and edits nothing.

P1.5.3 · The personal version

Create ~/.claude/commands/explain.md (outside this repository) with this content:
---
description: Explain a file in 5 bullets for exam study
---
Explain $ARGUMENTS in 5 bullets. Name any Claude Code feature involved.

Checkpoint ✅ /explain works in this session. Run git status in a second Terminal tab: .claude/commands/review.md shows as new, explain.md does not. Only the team command travels with the repository.

The exam lens. "Every developer gets it when they clone or pull" means .claude/commands/ in the repository. A home-folder location, a CLAUDE.md section or an invented config file are the distractors.

P1.6 · A skill that runs in a fork

15 min · 3.2

The one idea: some tasks read a lot of files but only need to return a short answer. context: fork runs the skill in a separate context. Only the result comes back, so your main conversation stays clean.

By the end you can: say when to use context: fork and how allowed-tools limits a skill.

P1.6.1 · Write the skill

Copy the whole box below — instruction and file together — and paste it into Claude Code as one message.

Create .claude/skills/codebase-map/SKILL.md with exactly this content:

---
name: codebase-map
description: Map an unfamiliar Python codebase. Use when the user asks what a codebase contains, where something lives, or how modules connect.
context: fork
allowed-tools: Read, Grep, Glob
---
Explore the codebase in the current folder.

Return ONLY this, under 15 lines:
- Modules: one line each, what it does
- Entry points: functions a caller would use first
- Tests: which modules have tests, which do not
- One risk you noticed, with the file name

Do not edit any file.

Two points about this file:

  • The description tells Claude when to use the skill. Claude can start it by itself when a request matches. A command never starts by itself.
  • allowed-tools lists only read-only tools. The skill cannot change code.

P1.6.2 · Run it two ways

  1. Type /exit and start claude again.
  2. Run it by name: type /codebase-map.
  3. Run it by description. In a fresh session, paste:

I'm new here. What does this codebase contain and where are the gaps in testing?

Checkpoint ✅ Both runs return a short map of 15 lines or fewer. The second run starts the skill without you naming it. The trace shows a separate task, and the many file reads stay out of your main conversation.

The exam lens. Verbose exploration filling the main context points to context: fork (or a subagent). A routine team prompt that a developer runs on purpose points to a command.

P1.7 · Commit, push, close

5 min

  1. Type /exit.
  2. In GitHub Desktop, check the changed files. You see p1-team-setup/ with CLAUDE.md, .claude/rules/, .claude/commands/, .claude/skills/, src/, tests/ and docs/.
  3. Write the summary P1 session 1: CLAUDE.md hierarchy, rules, command, skill.

Checkpoint ✅ The files are on github.com. Your user-level files (~/.claude/CLAUDE.md, ~/.claude/commands/explain.md) are not there. That is correct.

P1.8 · Quick reference card

User CLAUDE.md: ~/.claude/CLAUDE.md, only for you, never in git.
Project CLAUDE.md: repository root, for the whole team.
Directory CLAUDE.md: one folder, loaded when Claude works there.
@import: @path/file.md pulls a file into CLAUDE.md.
/memory: shows which memory files are loaded.
Rules: .claude/rules/*.md with a paths: glob. Follows a file type across folders.
Team command: .claude/commands/. Personal command: ~/.claude/commands/.
Skill: .claude/skills/<name>/SKILL.md. Description decides when it starts by itself.
context: fork: heavy work in a separate context, short result back.
allowed-tools: limits what a command or skill may do.
