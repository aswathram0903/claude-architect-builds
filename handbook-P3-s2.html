P3.9 · Why the schema passed a wrong total

15 min · 4.4

The one idea: a schema checks each value alone: is it a number, is it on the list. It cannot check whether values make sense together. Your own code must do that.

Two terms:

  • Schema error: a value of the wrong type or shape, for example text where a number belongs. Using a tool with a schema removes these.
  • Semantic error: every value has the right type, but together they are wrong, for example line items that do not add up to the total. Only checks in your code find these.

Open out/d-conflict.json from yesterday:

FieldValueSchema checkMakes sense?
stated_total1730✅ a number❌ The items add up to 1630
calculated_total1630✅ a number

That answers yesterday's open question. The schema saw two valid numbers. The conflict_detected flag only exists because we asked Claude to compare them. In the next step, your code checks this itself instead of trusting Claude's flag.

P3.10 · Check, retry once, route

25 min · 4.4 5.5

The one idea: when a check fails, ask again, but tell Claude exactly what failed. And know when asking again is useless: if the answer is not in the document, no retry can find it.

The script does four things for each invoice:

  1. Extract with yesterday's extract().
  2. Check with validate(). Each error is marked "retry can fix: True" or "False".
  3. Retry once, only for fixable errors. It sends back the document, the failed extraction and the specific error messages.
  4. Route: no errors left means AUTO-APPROVE. Anything left means HUMAN REVIEW, with the reasons.

To be sure you see one retry succeed, the script plants a format slip in a-tidy: it changes the invoice date to 14.09.2026 before the check. The retry must fix it.

P3.10.1 · Create the script

Start claude in p3-extraction and paste:

Create retry.py with exactly this content, and nothing else. Do not run it.

"""P3 session 2: check each extraction, retry once with the specific errors, then route."""
import json
import pathlib
import random
import re

from extract import INVOICE_TOOL, MODEL, SYSTEM, client, extract

DATE = re.compile(r"^\d{4}-\d{2}-\d{2}$")


def validate(d: dict) -> list[dict]:
    """Checks the schema cannot do. Each error says whether a retry can fix it."""
    errors = []
    items_sum = round(sum(item["amount"] for item in d.get("line_items", [])), 2)
    if abs(items_sum - d.get("calculated_total", 0)) > 0.01:
        errors.append({"field": "calculated_total", "retry": True,
                       "problem": f"calculated_total is {d.get('calculated_total')}, but the line item amounts add up to {items_sum}."})
    for field in ("invoice_date", "due_date"):
        value = d.get(field)
        if value is not None and not DATE.match(str(value)):
            errors.append({"field": field, "retry": True,
                           "problem": f"{field} is '{value}', which is not in YYYY-MM-DD format."})
    if d.get("stated_total") is not None and abs(d["stated_total"] - items_sum) > 0.01:
        errors.append({"field": "stated_total", "retry": True,
                       "problem": f"The stated total is {d['stated_total']}, but the line items add up to {items_sum}. "
                                  "Check that each amount is the line total, not the unit price."})
    if d.get("due_date") is None:
        errors.append({"field": "due_date", "retry": False,
                       "problem": "No due date in the document. Payment cannot be scheduled."})
    if d.get("currency") == "unknown":
        errors.append({"field": "currency", "retry": False,
                       "problem": "No currency in the document."})
    return errors


def retry_with_errors(text: str, failed: dict, errors: list[dict]) -> dict:
    """Send the document, the failed extraction and the specific errors back to Claude."""
    feedback = "\n".join(f"- {e['problem']}" for e in errors)
    response = client.messages.create(
        model=MODEL,
        max_tokens=1024,
        system=SYSTEM,
        tools=[INVOICE_TOOL],
        messages=[{"role": "user", "content":
            f"<document>\n{text}\n</document>\n\n"
            f"Your earlier extraction was:\n<extraction>\n{json.dumps(failed, indent=2)}\n</extraction>\n\n"
            f"It failed these checks:\n{feedback}\n\n"
            "Read the document again and call record_invoice with a corrected extraction. "
            "Fix only what the document supports. If the document itself is inconsistent, "
            "keep its values exactly as written and set conflict_detected to true."}],
    )
    for block in response.content:
        if block.type == "tool_use":
            return block.input
    raise RuntimeError(f"No tool call on retry. stop_reason={response.stop_reason}")


def process(path: pathlib.Path, simulate_slip: bool = False) -> dict:
    text = path.read_text()
    data = extract(text)
    if simulate_slip:
        data["invoice_date"] = "14.09.2026"  # a format slip, planted on purpose
    print(f"\n=== {path.stem} ===")
    errors = validate(data)
    for e in errors:
        print(f"  check 1: {e['field']}: {e['problem']}  [retry can fix: {e['retry']}]")
    fixable = [e for e in errors if e["retry"]]
    retried = False
    if fixable:
        data = retry_with_errors(text, data, fixable)
        retried = True
        errors = validate(data)
        for e in errors:
            print(f"  check 2 (after 1 retry): {e['field']}: {e['problem']}")
    decision = "AUTO-APPROVE" if not errors else "HUMAN REVIEW"
    print(f"  -> {decision}" + (" (fixed by retry)" if retried and not errors else ""))
    return {"document": path.stem, "decision": decision, "retried": retried,
            "reasons": [e["problem"] for e in errors], "extraction": data}


if __name__ == "__main__":
    results = []
    for p in sorted(pathlib.Path("docs").glob("*.txt")):
        results.append(process(p, simulate_slip=(p.stem == "a-tidy")))
    approved = [r for r in results if r["decision"] == "AUTO-APPROVE"]
    if approved:
        spot = random.choice(approved)
        spot["decision"] = "AUTO-APPROVE + SPOT CHECK"
        print(f"\nSpot check (random sample of auto-approved): {spot['document']}")
    out = pathlib.Path("out")
    out.mkdir(exist_ok=True)
    (out / "review_queue.json").write_text(json.dumps(results, indent=2))
    print("\nSummary:")
    for r in results:
        print(f"  {r['document']:14} {r['decision']}")

The exam lens, in plain words.

1. A retry works when the answer is in the document but came out in the wrong form. Example: a date in the wrong format, a unit price taken as a line total.

2. A retry cannot work when the information is not in the document. Example: no due date on the receipt. Send it to a person instead of retrying.

3. A useful retry sends three things back: the document, the failed extraction, and the exact error. "Try again" alone gives Claude nothing new.

4. Limit the retries. If it still fails after one, the problem is usually the document, not Claude.

Trap answer to spot: "retry up to 5 times until it passes". When the information is missing, more retries only increase the chance of an invented answer that passes.

P3.11 · Send all invoices as one batch

10 min · 4.5

The one idea: when nobody is waiting, send all requests in one batch. It costs about half as much, but you get no promise about when the results come back: often minutes, at most 24 hours.

Two terms:

  • Message Batch: one upload that holds many separate requests. Claude processes them in the background.
  • custom_id: your own label for each request. Results may come back in any order, so the label is how you match each result to its invoice.

The batch holds your 5 invoices, plus one request that is broken on purpose (z-broken, empty message), so you see how a failure looks.

P3.11.1 · Create and submit

Start claude and paste:

"""P3 session 2: send all invoices as one Message Batch, then collect results by custom_id."""
import json
import pathlib
import sys

from extract import INVOICE_TOOL, MODEL, SYSTEM, client

ID_FILE = pathlib.Path("out/batch_id.txt")


def submit() -> None:
    requests = []
    for p in sorted(pathlib.Path("docs").glob("*.txt")):
        requests.append({
            "custom_id": p.stem,
            "params": {
                "model": MODEL,
                "max_tokens": 1024,
                "system": SYSTEM,
                "tools": [INVOICE_TOOL],
                "messages": [{"role": "user", "content": f"<document>\n{p.read_text()}\n</document>"}],
            },
        })
    # One request that is broken on purpose, so you can see a failure by custom_id.
    requests.append({
        "custom_id": "z-broken",
        "params": {"model": MODEL, "max_tokens": 1024,
                   "messages": [{"role": "user", "content": ""}]},
    })
    batch = client.messages.batches.create(requests=requests)
    ID_FILE.parent.mkdir(exist_ok=True)
    ID_FILE.write_text(batch.id)
    print(f"Submitted {len(requests)} requests. Batch id: {batch.id}")
    print("Status:", batch.processing_status)


def status() -> None:
    batch = client.messages.batches.retrieve(ID_FILE.read_text().strip())
    print("Status:", batch.processing_status)
    print("Counts:", batch.request_counts)
    if batch.processing_status != "ended":
        print("Not finished yet. Run this again in a few minutes.")
        return
    failed = []
    for entry in client.messages.batches.results(batch.id):
        kind = entry.result.type
        if kind == "succeeded":
            data = next((b.input for b in entry.result.message.content if b.type == "tool_use"), None)
            vendor = data.get("vendor") if data else "(no tool call)"
            print(f"  {entry.custom_id:14} succeeded  vendor={vendor!r}")
        else:
            failed.append(entry.custom_id)
            print(f"  {entry.custom_id:14} {kind}")
    print("\nResubmit only these custom_ids:", failed or "none")


if __name__ == "__main__":
    {"submit": submit, "status": status}[sys.argv[1] if len(sys.argv) > 1 else "status"]()

P3.12 · Who decides: the human review queue

10 min · 5.5

The one idea: automation decides the easy cases. People decide the cases the checks cannot settle. The routing rule must be based on things your code can verify, not on how sure Claude says it is.

Open out/review_queue.json. Each invoice has a decision and its reasons. One auto-approved invoice is marked SPOT CHECK: the script picked it at random.

Routing signal in this scriptWhy it is trustworthy
A check failed after the retryYour code proved a problem
Information missing from the documentYour code saw a null where a value is required
Random spot check of approved invoicesMeasures how often "approved" is actually wrong

One signal is deliberately not used: asking Claude "how confident are you, 1 to 10?" Claude can be confidently wrong, as yesterday's few-shot test showed: services three times out of three, and wrong.

The exam lens, in plain words.

1. Route to people on signals you can check: failed validations, missing required fields, source conflicts.

2. A confidence score from the model is only usable after you have measured it against cases a person checked. Until then, treat it as unproven.

3. Also check a random sample of the auto-approved items. Otherwise you never learn how often the automation is wrong.

4. Measure accuracy per document type and per field, not as one overall number. A 97% average can hide one invoice layout that fails half the time.

Trap answer to spot: "send items to review only when the model's confidence is below 7". Uncalibrated confidence is not evidence.

P3.13 · Collect the batch by custom_id

10 min · 4.5

uv run python batch.py status

If it says "Not finished yet", wait 2–3 minutes and run it again.

Checkpoint ✅ When the status is ended:

  • Five invoices show succeeded, each with its vendor, matched by custom_id.
  • z-broken shows errored.
  • The last line says to resubmit only z-broken, not the whole batch.

The exam lens, in plain words.

1. Batch fits work where nobody waits: overnight reports, weekly audits. It does not fit anything a person or a merge is waiting for.

2. Plan with the worst case, not the usual case. Example: results are needed at 08:00 Monday and a batch can take up to 24 hours, so submit by 08:00 Sunday, not at midnight.

3. Match results by custom_id, never by order. Resubmit only the failed IDs, changed if needed (for example, split a document that was too long).

4. One batch request is one turn. It cannot call a tool, get the tool's result, and continue. Work that needs several tool steps cannot run inside a single batch request.

Trap answer to spot: "switch to batch, and fall back to real-time if it is slow". That adds complexity to a job that should never have been batch.

P3.15 · Quick reference card

Schema vs semantic: the schema checks each value's type; your code checks that values make sense together.
Retry works: the answer is in the document, but came out in the wrong form.
Retry cannot work: the information is not in the document. Route to a person.
A good retry sends: the document + the failed extraction + the exact error. One retry, then stop.
Route to people on: failed checks, missing fields, conflicts. Not on uncalibrated confidence.
Spot-check: a random sample of auto-approved items. Accuracy per document type and field.
Batch: about half the cost, up to 24 hours, no time promise. Only when nobody waits.
custom_id: match results by ID, resubmit only the failed IDs. One batch request = one turn, no tool loop.
