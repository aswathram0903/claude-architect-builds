P1.9 · Before you start

5 min

The one idea: this session uses npx, a tool that starts small Node.js programs without installing them permanently. Check it first.

  1. Open the Terminal and go to the project folder.
  2. Run this check:
cd ~/Documents/GitHub/claude-architect-builds/p1-team-setup && npx --version

Checkpoint ✅ You see a version number, and the prompt ends in p1-team-setup %. Stay in this folder for the whole session.

Why not uvx. An earlier version of this guide used Python servers through uvx. On an Intel Mac they try to compile a library from source and fail. The Node servers below need no compiling. The exam point is the same.

Do not start Claude Code yet. P1.10 starts it.

P1.10 · Shared and personal MCP servers

20 min · 2.4

The one idea: an MCP server gives Claude extra tools. Where you configure it decides who gets it, just like CLAUDE.md.

By the end you can: add a team server in .mcp.json that reads a value from an environment variable, add a personal server in ~/.claude.json, and show that Claude can use both at the same time.

ScopeFileWho gets it
Project.mcp.json at the repository rootEveryone who clones. Committed to git.
User~/.claude.json in your home folderOnly you. Never in git. Good for trials.

Two terms:

  • MCP server: a small program that gives Claude tools through a standard protocol (Model Context Protocol).
  • Environment variable: a named value set in your Terminal, for example DOCS_DIR=./src. Programs can read it. It is not saved in any file you commit.

P1.10.1 · The team server

The team server lets Claude read one folder of the project. The folder comes from an environment variable. Start Claude Code:

claude

Then paste:

Replace the whole content of .mcp.json in this folder (create it if it does not exist) with exactly this, and nothing else:

{
  "mcpServers": {
    "team-docs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "${DOCS_DIR:-./docs}"]
    }
  }
}

What ${DOCS_DIR:-./docs} means. Claude Code replaces it with the value of the environment variable DOCS_DIR. If that variable is not set, it uses ./docs. In a real team, the same pattern carries an API token, for example ${GITHUB_TOKEN}. The file is shared. The secret stays on each laptop.

P1.10.2 · The personal server

  1. Type /exit.
  2. In the Terminal (not inside Claude Code), run:
claude mcp add notes --scope user -- npx -y @modelcontextprotocol/server-memory
  1. Download both servers once, so the first start does not time out. Each command prints a little and then waits. Press Ctrl+C to stop it:
npx -y @modelcontextprotocol/server-filesystem ./docs
npx -y @modelcontextprotocol/server-memory
  1. Check both servers:
claude mcp list

Checkpoint ✅ The list shows notes and team-docs, among many others. If team-docs says it needs approval, that is expected. The next step approves it.

Why the list is long. Most entries come from your claude.ai account and installed plugins, not from this repository. Claude Code loads servers from several places, and all their tools are available together.

P1.10.3 · Use both at once, with a variable

  1. Set the variable and start Claude Code in the same command:
DOCS_DIR=./src claude
  1. Claude Code asks whether to use the MCP servers in .mcp.json. Approve team-docs.
  2. Type /mcp. Check that team-docs and notes show as connected. Press Escape.
  3. Paste:
Use only MCP tools for this, not Bash, Read, Grep or Glob.
1. Using the team-docs server: which directory are you allowed to read? List what is in it.
2. Using the notes server: store a note that says "P1 session 2: MCP scopes tested", then read it back.
For each answer, name the MCP server and the tool you used.

Checkpoint ✅ team-docs reads src, not docs, because DOCS_DIR was set. The note comes back from notes. Both servers' tools were available in the same session.

P1.10.4 · Prove what git sees

In a second Terminal tab, run:

git status --short

Checkpoint ✅ p1-team-setup/.mcp.json shows as new. ~/.claude.json does not show, because it is outside the repository. No folder value and no secret is in any committed file.

The exam lens, in plain words.

1. A tool the whole team needs goes in the shared project file, .mcp.json. Example: everyone uses Jira, so the Jira server goes there.

2. A password never goes in that shared file. Write a blank like ${JIRA_TOKEN}, and each person fills it in on their own laptop.

3. A tool only you are trying goes in your personal file, ~/.claude.json.

4. All connected tools work at the same time, in the same conversation.

Trap answer to spot: an option that writes a real password or token into a shared file.

One idea you do not build today: MCP resources. A server can also offer resources, which are read-only content lists such as a catalogue of issues or a database schema. Claude can see what exists without many exploratory tool calls. Resources are for content. Tools are for actions.

P1.11 · Plan mode, direct execution, Explore

20 min · 3.4

The one idea: the size and risk of the change decide the mode. Small and clear: do it. Large, multi-file or with design choices: plan first.

By the end you can: choose the mode for a task, switch into plan mode, and use the Explore subagent to keep a long search out of your conversation.

Two terms:

  • Plan mode: Claude reads and thinks, then shows a plan. It does not change any file until you approve.
  • Explore subagent: a built-in helper that searches the codebase in its own context and returns only a summary.

P1.11.1 · Task A — direct execution

A one-line change in one file. No design choice. Paste:

In src/orders/service.py, make cancel raise a ValueError with the message "Order already cancelled" if the order is already cancelled. Change only that function.

Checkpoint ✅ One small edit in one file. No plan was needed.

P1.11.2 · Task B — plan mode

  1. Press Shift+Tab until the status line under the prompt shows plan mode. It usually takes two presses.
  2. Paste:
Add an order priority (low, normal, high) that changes the order in which list returns orders: high first, then normal, then low, and oldest first inside each priority.
This touches the model, the service, the API and the tests.
Plan first. Give me the plan with the files you will change, the order of the changes, and any design choice I need to make.
  1. Read the plan. If it asks you a design question, answer it.
  2. Approve the plan when Claude Code offers to start. Claude Code leaves plan mode and makes the changes.

Checkpoint ✅ You saw a plan before any file changed. The changes touched four or more files.

P1.11.3 · Task C — the Explore subagent

Paste:

Use the Explore subagent for this. Find every place in this codebase where an order's status is set or changed. Return only a table: file, line, the status value, and the function. Do not edit anything.

Checkpoint ✅ The trace shows a separate Explore task. Your conversation gets only the short table, not every file the search read.

The exam lens, in plain words.

1. Small change, one place, and you know what to do: let Claude do it directly. Example: fix one function, add one check.

2. Big change, many files, or a design choice to make: plan mode first. Example: split an app into parts, replace a library used in 40 files.

3. Claude must read a lot just to find something: use the Explore subagent, so all that reading stays out of your conversation.

4. Often the best answer is both: plan mode to work out the plan, then direct execution to carry it out.

Trap answer to spot: "start directly and switch to planning if it gets hard", when the scenario already tells you the change is big.

P1.12 · Steer Claude to the right result

20 min · 3.5

The one idea: when prose gives inconsistent results, stop describing and start showing. Use an interview, concrete examples and tests.

By the end you can: use the interview pattern, give input/output examples, and drive a fix with failing tests.

P1.12.1 · The interview pattern

Paste, then answer each question in one or two lines:

I want a function format_order_summary(order) that returns a short text summary of an order for a customer email.
Before you write any code, interview me. Ask up to 4 questions, one at a time, about things I may not have thought of: missing values, formats, length, edge cases.
Write nothing until I have answered all of them.

Checkpoint ✅ Claude asked at least one question you had not thought of. Write that question down. That is the value of the pattern.

P1.12.2 · Input/output examples, then tests first

Paste:

Here are two concrete examples. Treat them as the specification.

Example 1
Input: Order(id="A-17", status="created", priority="high", items=3)
Output: "Order A-17 · 3 items · high priority · created"

Example 2
Input: Order(id="B-2", status="cancelled", priority="normal", items=1)
Output: "Order B-2 · 1 item · cancelled"

Notes: "item" is singular for 1. Normal priority is not shown.

Step 1: write tests in tests/test_summary.py from these two examples plus one edge case of your choice. Do not write the function yet.
Step 2: run the tests with: uv run --with pytest pytest -q
You may run that command. It does not add a dependency to the project.
Step 3: write format_order_summary in src/orders/summary.py. Run the tests again. Repeat until all pass.
Show me the test output after each run.

Checkpoint ✅ The first run fails, because the function does not exist yet. The last run passes. You saw Claude use the test failures to fix its code.

If the model fields in your codebase are different from the examples, Claude says so. Tell it to adapt the examples to the real fields.

The exam lens, in plain words.

1. Claude keeps getting the format wrong from your description: show it 2–3 examples of input and the exact output you want.

2. You do not know the area well: ask Claude to interview you before it builds.

3. You want it to improve step by step: write the tests first, then let Claude fix the code until they pass.

4. Several problems that affect each other: put them all in one message. Problems that do not affect each other: fix one at a time.

Trap answer to spot: more explanation in prose when the description is already being misread. Show, do not describe.

P1.13 · Name, resume and fork a session

15 min · 1.7

The one idea: resume a session when what Claude saw is still true. Start fresh with a summary when the files have changed under it.

Two terms:

  • Resume: open an earlier conversation and continue with all its context.
  • Fork: make a copy of a conversation, so you can try a different approach without changing the original.

P1.13.1 · Name this session and leave

  1. Type /rename p1-priority-work.
  2. Type /exit.

P1.13.2 · Change a file behind Claude's back

Open src/orders/summary.py in any text editor. Add this line at the top and save:

# Summary format agreed with support team, 24 Oct

P1.13.3 · Resume and tell it what changed

claude --resume p1-priority-work

If the name does not work, run claude --resume and pick the session from the list. Then paste:

Since we last spoke, I edited src/orders/summary.py by hand (I added a comment at the top). Re-read that file before you rely on anything you saw earlier. Then tell me in one line what changed.

Checkpoint ✅ Claude re-reads the file and reports the new comment. It continued with all the earlier context of the session.

P1.13.4 · Fork to try another approach

  1. Type /exit.
  2. Run:
claude --resume p1-priority-work --fork-session
  1. Paste:
This is a fork. Without changing any file, describe in 5 lines how you would implement priority as an integer (1-3) instead of a text value, and what that would change in the tests.

Checkpoint ✅ The fork knows the whole priority discussion. The original session p1-priority-work is unchanged. Check with claude --resume: both sessions show in the list.

The exam lens, in plain words.

1. You come back to yesterday's work and little has changed: resume the session, and tell Claude which files you changed.

2. A lot has changed since: start a new session and give it a short summary of what you concluded. The old session holds old file contents that would mislead it.

3. You want to try two approaches from the same starting point: fork the session.

Trap answer to spot: resuming a session as if nothing changed.

P1.15 · Quick reference card

Team MCP server: .mcp.json, committed. Secrets as ${VARIABLE}.
Personal MCP server: ~/.claude.json (claude mcp add --scope user). Not in git.
All servers' tools: available at the same time. /mcp shows them.
Resources: content catalogues. Tools: actions.
Direct execution: small, clear, one place. Plan mode: many files, design choices.
Explore subagent: long discovery, short summary back.
Inconsistent output: 2–3 input/output examples. Unclear requirements: interview. Progressive fixes: tests first.
Interacting issues: one message. Independent issues: one at a time.
Resume: context still valid, tell it what changed. Fresh + summary: context stale. Fork: two approaches from one baseline.
